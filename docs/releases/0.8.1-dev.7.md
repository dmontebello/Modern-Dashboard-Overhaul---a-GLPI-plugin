# 0.8.1-dev.7 — Form unico Nuova task
**Stato:** candidata tecnica sul branch di sviluppo; **NON COLLAUDATO LIVE** su GLPI 11.0.9.

## Fix e feature
- Un solo pulsante Nuova task e form POST `front/task.form.php` con nome, descrizione, scadenza e progetto facoltativo.
- `projects_id>0` validato lato server crea la ProjectTask **nativa** via `check(-1, CREATE)` e `add`, esclusivamente dopo `TaskBoard::canCreateInProject`; nessun progetto fittizio o scrittura SQL sul core.
- `projects_id=0` o campo vuoto crea la StandaloneTask solo con CREATE, abilitazione del modulo e diritti item; non si converte una task esistente. Metadati entity/status/assegnatario/gruppo riguardano **solo** questo ramo. Non trasferire questi ID nei campi Team/ProjectState della ProjectTask.
- Campi condivisi mappati: nome, descrizione, scadenza `due_date` -> `plan_end_date` (progetto) / `due_date` (indipendente); i campi avanzati ProjectTask sono nel form core dopo la creazione. Diari e allegati dev.6 restano accessibili a task creata.
- GET nuova task non scrive sul database, POST richiede CSRF middleware GLPI11, rifiuta valori/ID illegittimi e conserva i valori su errore; redirect fuori dal catch del modello.
- I vecchi URL `tasks.php?new=1&kind=project` restano nel codice per compatibilità; `new=1` senza kind inoltra al form unico.

## Rischi e scarti
La selezione progetto rimane il dropdown nativo GLPI. Le task di progetto non supportano direttamente nel form unificato la configurazione di team multipli, parent task, durate o stato nativo; questi attributi vengono modificati nella scheda GLPI dopo la creazione. L'assenza di progetto non deve silenziosamente creare ProjectTask né aggiungere un progetto nascosto. Nessuna nuova tabella o modifica allo schema 2 rispetto a dev.6.

## Rollback
Backup coordinato database, plugin, configurazione e volume `GLPI_DOC_DIR/mdoverhaul` prima del test in staging. Spegnere `task_workspace` per un rollback funzionale non distruttivo. Per ripristino completo usare snapshot coerente; le nuove task create dopo il backup sono dati da esportare prima di tornare indietro. Non usare un downgrade parziale di schema/volume.

## SHA512 e build-info.json
La pipeline genera ZIP versionata immutabile, checksum SHA512 e `build-info.json` con source SHA, run ID e UTC. Non inserire valori inventati prima del build.
